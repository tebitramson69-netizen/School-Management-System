1. Executive Summary

This is a custom-built, framework-free PHP 8 MVC application that manages the academic operations of a Cameroonian Anglophone secondary school: user accounts across four roles, classes and subjects, teacher assignments, attendance, score entry per sequence, coefficient-weighted averages, grading, class rankings, report cards and announcements.

It is a genuinely substantial system — roughly 19,300 lines across 74 files, with a clean separation between a front controller, controllers, models, middleware and views. It is not a tutorial project. The domain logic in particular (term/sequence aggregation, coefficient weighting, competition-style ranking) reflects real understanding of how Cameroonian secondary schools actually compute results.

The honest one-paragraph verdict. The security fundamentals and the domain modelling are well above what this kind of project usually shows — CSRF at a single chokepoint, prepared statements without exception, and a ranking engine deliberately built to share one averaging definition with the report card are all senior-level decisions. What stands between this and a deployable product is not architecture; it is three concrete blockers (§13.1, §14.1, §14.3), a hard-coded pass mark that is wrong for Cameroon (§14.2), and the absence of edit/delete operations. Those are days of work, not months.

2. Domain Primer — The Cameroon GCE System

2.1 Why a developer must read this first

Most of the non-obvious code in this project exists because of how Cameroonian schools grade. A developer who skips this section will read the terms table or Score::subjectAveragesForStudentTerm() and conclude they are buggy. They are not — they encode real rules.

2.2 Terms, sequences and the 0–20 scale

ConceptMeaning in this system
CyclesFirst Cycle covers Forms 1–5, ending with the GCE Ordinary Level at Form 5. Second Cycle covers Lower Sixth and Upper Sixth, ending with the GCE Advanced Level.
Academic yearNamed like 2026/2027. Exactly one is flagged current at a time.
TermThree per academic year: Term 1, Term 2, Term 3.
SequenceEach term contains two assessment sequences, giving six sequences per year. A subject's term mark is the mean of its two sequence marks.
Marking scaleEvery mark is out of 20. The database stores score and max_score, with max_score fixed at 20.00 on insert.
Pass mark10 out of 20 is the standard threshold. It is configurable in school_settings.pass_mark — but see §14.2, where the code ignores that column.

2.3 Coefficients and weighted averages

Subjects are not equal. A science stream weights Physics and Mathematics more heavily than, say, Food Science. Each subject carries a coefficient — an integer multiplier — and the overall average is:

overall average = Σ(subject_average × coefficient) / Σ(coefficients)

Coefficients are standardised by MINESEC but vary by class and stream, so this system stores them per subject per class in the subject_coefficients table and lets an administrator edit them. A plain arithmetic mean of subject marks is mathematically wrong for a Cameroonian report card — which is why the weighting logic in §9.3 matters so much.

5. Architecture

5.1 Layering

The application is a hand-rolled MVC with four clear layers and no framework underneath:

Browser │ GET/POST index.php?action=… ▼ ┌──────────────────────────────────────────────────────────────┐ │ FRONT CONTROLLER public/index.php │ │ · configures + starts the hardened session │ │ · validates CSRF for EVERY POST (single chokepoint) │ │ · switch($action) → require controller → call method │ └───────────────────────┬──────────────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────────┐ │ MIDDLEWARE AuthMiddleware::requireRole() │ │ · authenticated? · role allowed? · must change password? │ └───────────────────────┬──────────────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────────┐ │ CONTROLLERS Auth · Admin · Teacher · Student · Parent · │ │ AcademicYear │ │ · input validation · ownership checks · orchestration │ └───────────────────────┬──────────────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────────┐ │ MODELS (16) all SQL lives here, all via PDO prepares │ │ Score · Result · Term · Student · SubjectCoefficient · … │ └───────────────────────┬──────────────────────────────────────┘ ▼ MySQL · 12 tables · utf8mb4 ▲ ┌───────────────────────┴──────────────────────────────────────┐ │ VIEWS ob_start() → $content → views/layouts/dashboard.php │ │ shared header + role-aware sidebar │ └──────────────────────────────────────────────────────────────┘

The layering is respected. Every SQL statement found in the codebase lives in src/Models/. Controllers never query the database directly, and views never do either — they receive prepared variables. That discipline is what makes this codebase extensible, and it should be defended in review.

5.2 Front controller & request lifecycle

Every request enters through public/index.php and follows the same path:

  1. Configuration — config/database.php loads .env and defines BASE_URL and SCHOOL_EMAIL_DOMAIN.
  2. Session hardening — Security::configureSession() sets httponly, samesite=Strict, use_strict_mode and use_only_cookies before session_start(). Order matters: these ini_set() calls are no-ops once a session exists, which is why the method returns early if one is already active.
  3. Action resolution — $action = trim($_GET['action'] ?? 'login'), defaulting to the login page.
  4. Global CSRF gate — if the method is POST, Security::requireValidCsrf() runs before any route is dispatched.
  5. Dispatch — a switch maps the action to a controller method. Controllers are required inside their own case, so a login request never loads the admin controller or its models.
  6. Authorization — the controller method's first statement is AuthMiddleware::requireRole(...).
  7. Response — write actions redirect (Post/Redirect/Get); read actions render a view through the shared layout.

Global CSRF validation is the single best decision in this codebase. Most PHP projects validate CSRF inside each handler, and the first handler someone forgets becomes the vulnerability. Here it is structurally impossible to add an unprotected POST route — the gate sits above the router. Preserve this property in any refactor.

5.3 The view layout system

Views use output buffering to inject their body into shared chrome:

$pageTitle = 'Admin Dashboard';
ob_start();
    // ... the page's own HTML ...
$content = ob_get_clean();
require __DIR__ . '/../layouts/dashboard.php';

views/layouts/dashboard.php then renders components/header.php, the role-aware components/sidebar.php, and drops $content into the main region. Verified: every one of the 23 page views uses this layout. The only file that does not is views/student/_header.php, a partial, whose leading underscore correctly signals that.

Note: both CLAUDE.md and PROJECT_PROGRESS.md still describe layout migration as outstanding work. It is complete — see §15.

7. Authentication & Authorization

7.1 Login flow

AuthController::login() executes these checks in order, and each failure exits immediately:

  1. Reject non-POST requests.
  2. Security::checkLoginRateLimit() — blocks after 5 failures for 5 minutes.
  3. Both fields present; email passes FILTER_VALIDATE_EMAIL.
  4. Look up the user; verify with password_verify().
  5. On failure, record the attempt and return the same message — "Invalid email or password." — whether the email exists or not. This is deliberate: a distinct "no such account" message would let an attacker enumerate valid addresses.
  6. Reject deactivated accounts (is_active = 0).
  7. session_regenerate_id(true) — issues a new session ID on privilege change, defeating session fixation.
  8. Store only user_id, email, role, must_change_password in the session. No password hash, no full user row.
  9. Redirect to the role's dashboard; an unrecognised role triggers a logout rather than falling through.

7.2 Role enforcement

AuthMiddleware::requireRole(string|array $allowedRoles) is the single authorization primitive. It verifies a session exists, normalises the allowed roles to an array, and compares with in_array($currentRole, $allowedRoles, true) — strict comparison, so no type-juggling bypass. Unauthorised users get HTTP 403 and a rendered page; unauthenticated users are redirected to login.

Verified: every controller action calls it. The student controller does so through a shared private helper:

private function bootStudentContext(): array
{
    AuthMiddleware::requireRole('student');
    // … resolve user → student profile → current class → school settings
    return ['student' => $student, 'studentId' => $studentId,
            'classId' => $classId, 'school' => $school];
}

Each of the four student pages begins with $context = $this->bootStudentContext();. This is the right pattern: authorization cannot be omitted from a new student page without also omitting the data the page needs, so the two failure modes collapse into one that is immediately visible.

Ownership checks beyond role

Role alone is insufficient — one teacher must not mark another's class, and one parent must not read another family's child. Both are handled:

// TeacherController — mark attendance / enter scores
$assignment = $this->assignmentModel->find($assignmentId);
if (!$assignment || (int) $assignment['teacher_id'] !== $teacher['id']) {
    http_response_code(403);
    echo "Access denied. This is not your assignment.";
    exit;
}

// ParentController — child detail
if (!$this->parentModel->isLinkedToChild($parent['id'], $studentId)) {
    http_response_code(403);
    echo "Access denied. This is not your child.";
    exit;
}

These are Insecure Direct Object Reference defences, and they are correctly placed before any data is loaded. This is the class of check most projects of this size omit entirely.

7.3 Forced password change

Accounts are created with must_change_password = TRUE. The middleware redirects such users to the change-password page on every request — explicitly exempting change_password_form and change_password themselves, which is what prevents an infinite redirect loop. The exemption is the subtle part; do not remove it.

8.3 The terms/sequence modelling decision

This is the single most important thing to understand before touching the grading code.

A row in terms is not a term — it is a term-sequence. "Term 1" with two sequences is two rows:

idacademic_year_idnamesequence_numberis_current
11Term 110
21Term 121
31Term 210

A term is therefore identified by the pair (academic_year_id, name), not by a single id. This is why Score::subjectAveragesForStudentTerm() contains a self-join that looks unnecessary at first reading:

INNER JOIN terms selected_term ON selected_term.id = :term_id
WHERE sc.student_id = :student_id
  AND sc.term_id IN (
        SELECT t.id FROM terms t
        WHERE t.name = selected_term.name
          AND t.academic_year_id = selected_term.academic_year_id
  )

It takes the given term-sequence row, recovers its name and year, and then averages across all sequences of that term. Without it, a "term average" would only ever reflect one sequence. Any new query that aggregates by term must reproduce this pattern — and §14.4 documents the one place that does not.

Redundancy to be aware of. scores.sequence and terms.sequence_number both record the sequence. Nothing in the schema forces them to agree, so a row can claim sequence = 1 while its term_id points at the sequence-2 term row. The application never writes such a row today, but a future bulk import could. Longer term, the cleaner model is a terms table holding three real terms and letting scores.sequence be the only sequence marker. That is a migration, not a quick fix — plan it, do not improvise it.

9. The Academic Engine

This is the core of the product and deserves the closest reading. Four classes cooperate: Score (761 lines), Result (462), SubjectCoefficient (280) and GradeScale (22).

9.1 Score entry

Score::recordBulk() saves a whole class's marks for one subject, term and sequence:

INSERT INTO scores (student_id, subject_id, term_id, sequence, score, max_score)
VALUES (:student_id, :subject_id, :term_id, :sequence, :score, 20.00)
ON DUPLICATE KEY UPDATE score = VALUES(score), max_score = VALUES(max_score)

Four properties are worth naming:

  • Idempotent. ON DUPLICATE KEY UPDATE combined with the unique key means re-submitting the form corrects marks rather than duplicating them.
  • Transactional. The whole batch is wrapped in beginTransaction() / commit(), with rollback guarded by inTransaction(). One invalid mark rejects the entire batch — the correct choice, since a half-saved register is worse than a rejected one.
  • Validated. Non-numeric values and marks outside 0–20 throw InvalidArgumentException; the identifiers are rejected if non-positive.
  • Blank means ungraded. Empty strings are skipped, not stored as zero. This matters: a missing mark and a mark of zero are different facts, and conflating them would drag a student's average down.

9.2 Subject averages and term aggregation

Score::subjectAveragesForStudentTerm($studentId, $termId) returns one row per subject with average_score, sequence_count and max_score, averaging across every sequence of the term via the self-join described in §8.3. This is the method the report card renders.

9.3 Coefficient-weighted overall average

Score::overallAverageForStudentTerm($studentId, $termId, $classId = 0) implements the Cameroon formula:

$coefficients = $classId > 0
    ? (new SubjectCoefficient())->getForClass($classId)   // [subject_id => coefficient]
    : [];

foreach ($subjects as $subject) {
    if ($subject['average_score'] === null) continue;

    $coefficient = $coefficients[(int) $subject['subject_id']] ?? 1;

    $weightedTotal     += (float) $subject['average_score'] * $coefficient;
    $totalCoefficients += $coefficient;
}

return $totalCoefficients === 0
    ? null
    : round($weightedTotal / $totalCoefficients, 2);

The ?? 1 default is the important detail: a subject with no configured coefficient falls back to weight 1, so the formula degrades gracefully to a plain mean rather than dropping the subject or dividing by zero. Ungraded subjects are skipped entirely, and an empty result returns null — not 0, which would be indistinguishable from a genuine zero average.

This is correct, and it is the feature that makes the system usable in a Cameroonian school. Both project notes still list weighted averages as an unimplemented gap; that is stale (§15).

9.4 Grade scale

Letters and remarks are never hard-coded. Result::getGrade() and GradeScale::forScore() both query the grade_scale table:

SELECT id, min_score, max_score, letter, remark
FROM grade_scale
WHERE :score >= min_score AND :score <= max_score
ORDER BY min_score DESC
LIMIT 1

Seeded bands: A 16–20 Excellent, B 14–15.99 Very Good, C 12–13.99 Good, D 10–11.99 Fair, E 8–9.99 Weak, F 0–7.99 Fail. An administrator can change the policy without touching a single stored score.

A latent portability trap. This query binds the named placeholder :score twice. PDO's emulated prepares — the MySQL default, and what this project runs with — expand it fine. Native prepares do not: reusing a named placeholder raises HY093 Invalid parameter number. So the day someone hardens the connection with PDO::ATTR_EMULATE_PREPARES => false (normally good advice), every grade lookup in the system breaks. Fix it pre-emptively by binding two distinct placeholders, :score_min and :score_max, with the same value.

9.5 Class rankings

Result::getClassResults($classId, $academicYearId, $termId) builds the ranking:

  1. Load every student enrolled in the class for that academic year.
  2. Compute each student's overall result — delegating the average to Score::overallAverageForStudentTerm().
  3. usort() by average descending, with students who have no results forced to the bottom and ties broken by name.
  4. Assign competition-style positions: equal averages share a position and the next distinct average skips accordingly (1st, 2nd, 2nd, 4th). Students without results get position = null rather than a misleading last place.

One definition of "average", by construction. The ranking does not re-implement averaging — it calls the same Score method the report card calls. This is deliberate and the code comments say so. It means a student's displayed average and the average their rank was computed from can never drift apart. If you ever need to change the averaging rule, change it in Score only; do not add a second implementation.

Performance: this is an N+1 pattern. Ranking a class runs roughly three queries per student — subject results, subject averages, and the coefficient lookup, the last of which fetches the same per-class coefficient map once per student. A 60-student class costs around 180 queries, and the student report card triggers a full class ranking just to find one position. It is tolerable at a single school's scale, but it is the first thing that will hurt. Two cheap fixes: hoist the coefficient lookup out of the loop (it is identical for every student in the class), and compute the whole class's subject averages in one grouped query instead of one query per student.

12. Installation & Setup

A fresh clone will not run. config/database.php begins with require_once __DIR__ . '/env.php';, but config/env.php is listed in .gitignore and is not in the repository. Every request fatals before reaching the router. Step 4 below is the workaround; §14.1 is the real fix.

  1. Start XAMPP — Apache and MySQL.
  2. Clone into the web root, e.g. C:\xampp\htdocs\school-system. The folder name must match the path segment in BASE_URL.
  3. Create the database and schema: 
    CREATE DATABASE `school-system`

SOURCE database/migration_002_pass_mark.sql;
SOURCE database/migration_003_terms_unique_constraint.sql;
  4. Recreate config/env.php — it must define an env($key, $default) function that reads .env. See §14.1 for why this file belongs in version control and .env does not.

  6. Seed the first administrator. There is no installer and no registration page, so the first account must be created by hand. Generate a hash with php -r "echo password_hash('YourStrongPass1', PASSWORD_DEFAULT);", then:

13. Security Review

Findings are ordered by severity, each with root cause before remedy.

13.1 CRITICAL Source and secrets are exposed over HTTP

Root cause: .htaccess at the project root is 0 bytes, and the documented BASE_URL is /school-system/public — meaning Apache serves the entire project directory, not just public/. Nothing restricts access to the parent folders.

Impact: with the project at htdocs/school-system, these are all fetchable by anyone who can reach the server:

http://host/school-system/.env                    → database credentials
http://host/school-system/config/database.php     → served as PHP, but...
http://host/school-system/database/schema.sql     → full schema, downloaded as text
http://host/school-system/src/Models/Score.php    → source if PHP handling is ever misconfigured

The .sql files and .env are not PHP, so Apache returns them as plain text immediately. Database credentials leak on the first request.

Fix — do both:

  1. Point the virtual host's DocumentRoot at public/. This is the real fix. Nothing outside public/ is then addressable at all, and BASE_URL becomes /.
  2. Add defence in depth in the root .htaccess, for shared hosting where you cannot set the document root: 
    # Block everything at the project root except the public/ entry point
<FilesMatch "\.(env|sql|md|json|lock|ini|log)$">
    Require all denied
</FilesMatch>

RedirectMatch 403 ^/school-system/(config|src|database|views)/.*$

Treat any credentials that have been live on an exposed host as compromised and rotate them.

13.2 STRONG Injection, CSRF and XSS defences

These are done properly and are recorded here so a future reviewer does not "fix" them into something worse:

  • SQL injection — every query in all 16 models uses PDO prepared statements with named parameters. No string interpolation into SQL was found anywhere in the codebase.
  • CSRF — validated once, globally, for every POST before routing (§5.2). Tokens are 32 random bytes compared with hash_equals().
  • XSS — 167 escaped outputs with ENT_QUOTES and explicit UTF-8; integers cast before echo.
  • Session fixation — session_regenerate_id(true) on successful login.
  • IDOR — ownership verified for teacher assignments and parent–child links.
  • User enumeration — identical error message whether or not the email exists.

13.3 MEDIUM Database errors and internal messages reach the browser

Root cause: config/database.php ends its catch block with die("Database connection failed: " . $e->getMessage()). Several controllers likewise echo a message and exit on missing profiles.

Impact: a connection failure prints the host, database name and driver error to the visitor.

Fix: log with error_log(), render a neutral page, and in production set display_errors = Off with log_errors = On. Replace the bare echo+ exit paths with a small shared error view so failures look like the rest of the application.

13.4 MEDIUM Rate limiting is per-session, not per-account

Root cause: the attempt counter lives in $_SESSION.

Impact: an attacker who discards the session cookie between attempts gets an unlimited allowance. The control stops an honest user fat-fingering a password; it does not stop a scripted attack.

Fix: record attempts in a login_attempts(email, ip_address, attempted_at) table and throttle on the email/IP pair. The existing session check can stay as a cheap first line.

13.5 LOW CSRF token never rotates

The token is generated once per session and reused until logout. Rotating it after each successful state-changing POST narrows the window in which a leaked token is useful. Low priority given the samesite=Strict cookie already in place.

13.6 LOW No security headers

No Content-Security-Policy, X-Frame-Options, X-Content-Type-Options or Referrer-Policy is sent. Adding them in .htaccess costs four lines and mitigates clickjacking, MIME sniffing and referrer leakage. Note that a strict CSP will require removing the inline style="…" attributes and onclick handlers currently present in several views.

14. Verified Defects & Root-Cause Analysis

Every defect below was confirmed against the source at commit e9f23ca. Claims from the project's own notes that did not survive verification are listed separately in §15.

14.1 CRITICAL A fresh clone cannot boot — config/env.php is git-ignored

Where: .gitignore lines 3–6; config/database.php line 18.

# .gitignore
.env
config/env.php          ← this is the problem

Root cause: two different kinds of file were treated as one. .env holds secrets and must never be committed. config/env.php is the parser that reads .env — it is ordinary application code containing no secrets, and config/database.php requires it unconditionally on line 18. Ignoring it means the repository is missing a file it cannot run without.

Symptom: Fatal error: Failed opening required '.../config/env.php' on every request after a clean clone. Verified: the file is absent from the repository, and .env.example is the only env-related file tracked.

Fix: remove config/env.php from .gitignore and commit it. Keep .env ignored — that line is correct and should stay. Also note .env is listed twice in the file; harmless, but tidy it. If env.php has been lost locally, it needs to be re-authored:

<?php
declare(strict_types=1);

function env(string $key, ?string $default = null): ?string
{
    static $vars = null;

    if ($vars === null) {
        $vars = [];
        $path = __DIR__ . '/../.env';

        if (is_readable($path)) {
            foreach (file($path, FILE_IGNORE_NEW_LINES | FILE_SKIP_EMPTY_LINES) as $line) {
                $line = trim($line);
                if ($line === '' || $line[0] === '#' || !str_contains($line, '=')) {
                    continue;
                }
                [$name, $value] = explode('=', $line, 2);
                $vars[trim($name)] = trim($value, " \t\n\r\0\x0B\"'");
            }
        }
    }

    return $vars[$key] ?? $default;
}

This is a reconstruction consistent with how config/database.php calls env(), not a copy of the original file — the original is not in the repository to compare against.

14.2 HIGH Pass/fail uses a hard-coded 8.00 and ignores the configured pass mark

Where: src/Models/Result.php, determinePassFail().

public function determinePassFail(float $average): string
{
    return $average >= 8.00 ? 'PASS' : 'FAIL';
}

Root cause: the method predates migration_002_pass_mark.sql, which added school_settings.pass_mark DECIMAL(5,2) NOT NULL DEFAULT 10.00. That migration's own header states: "The Result model reads this to decide PASS/FAIL." It does not — the constant was never replaced. SchoolSettings::get() already selects the column and even falls back to '10.00', so the value is available and simply unused.

Impact: this is a correctness bug with real consequences, not a style issue. The Cameroon pass mark is 10/20, and the seeded grade scale marks 8–9.99 as "E — Weak". Every student averaging between 8.00 and 9.99 is currently reported as PASS when the school's own configured threshold says they have failed. It also silently propagates into getClassSummary(), inflating the reported pass rate.

Fix: read the configured value, defaulting to 10.00:

public function determinePassFail(float $average): string
{
    $passMark = (float) (School::settings()['pass_mark'] ?? 10.00);

    return $average >= $passMark ? 'PASS' : 'FAIL';
}

Then delete the now-inaccurate docblock above the method, which still describes the 8.00 rule as "the current school rule".

14.3 HIGH A view include breaks on Linux due to file casing

Where: src/Controllers/TeacherController.php line 77.

require __DIR__ . '/../../views/teacher/mark_attendance.php';   // lowercase m
// file on disk:   views/teacher/Mark_attendance.php            // uppercase M

Root cause: Windows and macOS default to case-insensitive filesystems, so the mismatch is invisible during XAMPP development. Linux — where this will be deployed — is case-sensitive.

Impact: the teacher attendance page fatals on any Linux host. Verified by resolving every require/include path in the project against the actual filesystem; this was the only genuine casing mismatch found.

Fix: rename the file, preserving history and forcing Git to record the case change:

git mv views/teacher/Mark_attendance.php views/teacher/mark_attendance.tmp
git mv views/teacher/mark_attendance.tmp  views/teacher/mark_attendance.php

The two-step rename is necessary because Git on a case-insensitive filesystem ignores a direct case-only rename.

Prevent the whole class of bug with a CI check that resolves every include path against the filesystem on Linux. Three lines in a workflow will catch this permanently — see §16, Phase 1.

14.4 MEDIUM Two different "subject results" definitions coexist

Where: Score::subjectAveragesForStudentTerm() versus Result::getStudentSubjectResults().

Root cause: the Score version aggregates across every sequence sharing the term's name and academic year (§8.3). The Result version filters on sc.term_id = :term_id exactly — a single sequence. The two were written at different times and the second never adopted the aggregation rule.

Impact: the overall average is computed from the aggregated set, but subject_count inside getStudentOverallResult() is counted from the non-aggregated one. A student with marks in both sequences can therefore be shown an overall average derived from, say, eight subjects alongside a subject count of five. The overall figure itself is correct; the count beside it is not, and the per-subject grades returned by getStudentClassPosition() reflect one sequence rather than the term.

Fix: delete Result::getStudentSubjectResults() and have Result call Score::subjectAveragesForStudentTerm(), exactly as it already does for the overall average. One definition of a subject average should exist in the codebase, and Score is the right home for it.

14.5 MEDIUM User::updatePassword() cannot report failure

Where: src/Models/User.php and AuthController::changePassword().

// Model — declared void, returns nothing
public function updatePassword(int $userId, string $newPassword): void

// Controller — checks a return value that can never be false
$updated = $this->userModel->updatePassword(...);
if ($updated === false) { /* unreachable */ }

Root cause: the model's contract and the controller's expectation disagree. A void function evaluates to null, and null === false is false, so the guard never fires.

Impact: limited in practice, because PDO is configured with ERRMODE_EXCEPTION, so a genuine database failure throws rather than returning quietly. But the controller contains dead error-handling that gives a false impression of safety, and if a caller ever uses a driver without exception mode, a failed password change reports success.

Fix: change the signature to : bool and return $stmt->execute([...]);. The controller's existing check then works as written.

14.6 MEDIUM "Latest term" is chosen by highest id, not by date

Where: Score::latestTermIdForStudent() — ORDER BY term_id DESC LIMIT 1.

Root cause: the query assumes a higher terms.id always means a chronologically later term-sequence. That holds only while terms are inserted in calendar order and never backfilled.

Impact: if a term is ever added out of order — correcting a missed year, importing history, re-seeding — students' report cards silently display the wrong term.

Fix: add start_date/end_date to terms and order by date; or, as a smaller step, join academic_years and order by (ay.name DESC, t.name DESC, t.sequence_number DESC), which encodes the real intent rather than relying on insertion order.

14.7 LOW Grade lookup breaks if prepared-statement emulation is disabled

Covered in §9.4. Two distinct placeholders instead of one reused :score.

14.8 LOW Ranking is an N+1 query pattern

Covered in §9.5. Hoist the per-class coefficient lookup out of the per-student loop and batch the subject averages.

Appendix C — Glossary

TermMeaning in this project
SequenceOne of two assessment periods within a term. Six per academic year.
Term-sequence rowA row in terms. A term is the pair (academic_year_id, name), not one row — §8.3.
CoefficientInteger weight for a subject within a class, used by the overall average — §9.3.
GCEGeneral Certificate of Education — the Cameroonian Anglophone examination, O/L at Form 5 and A/L at Upper Sixth.
MINESECCameroon's Ministry of Secondary Education, which standardises subject coefficients.
Front controllerA single entry point (public/index.php) through which every request passes before routing.
MiddlewareA check that runs between routing and the controller body — here, AuthMiddleware::requireRole().
CSRFCross-Site Request Forgery — making a logged-in user's browser issue a state-changing request. Blocked globally here.
IDORInsecure Direct Object Reference — reaching another user's record by changing an id in the URL. Guarded for teacher assignments and parent–child links.
N+1 queriesRunning one query per item in a loop instead of one query for the whole set — §9.5.
Post/Redirect/GetRedirecting after a successful POST so a refresh cannot resubmit it. Applied after every write.
Emulated preparesPDO building the final SQL string in PHP rather than sending a parameterised statement to MySQL. On by default; §9.4 explains why that currently matters.
